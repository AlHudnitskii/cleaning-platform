# Архитектурные решения (ADR)

Короткие записи о решениях, которые определяют устройство системы: почему выбрано именно так и чем за это заплачено. Формат: контекст → решение → последствия → отвергнутые альтернативы.

## ADR-001. Transactional outbox для событий

**Контекст.** После изменения задачи нужно уведомить исполнителя (Web Push) и обновить открытые экраны (SSE). Если публиковать в RabbitMQ прямо из обработчика запроса, возможны два сбоя: транзакция зафиксирована, а публикация упала (уведомление потеряно), или публикация прошла, а транзакция откатилась (уведомление о несуществующем изменении).

**Решение.** Обработчик пишет событие в таблицу `outbox_messages` в той же транзакции, что и изменение. Отдельный процесс relay пачками забирает неопубликованные строки с `FOR UPDATE SKIP LOCKED`, публикует в fanout-обменник `task_events` с подтверждением брокера и только потом ставит `published_at`.

**Последствия.** Доставка «как минимум один раз»: при падении relay между публикацией и отметкой событие уйдёт повторно, поэтому потребители не должны ломаться от дублей. Задержка уведомления — интервал опроса relay. Несколько экземпляров relay безопасны благодаря `SKIP LOCKED`. Частичный индекс по `published_at IS NULL` держит выборку быстрой при росте таблицы.

**Отвергнуто.** Публикация из обработчика (теряет события); двухфазный коммит с брокером (RabbitMQ его не поддерживает, сложность несоразмерна); CDC через логическую репликацию (ещё один компонент в эксплуатации).

## ADR-002. Иерархия локаций в PostgreSQL ltree

**Контекст.** Локации образуют дерево «страна → город → здание → этаж → помещение». Нужны выборки поддерева (задачи в здании со всеми этажами и помещениями) и полные имена вида «Germany / Berlin / Berlin HQ».

**Решение.** Каждая локация хранит `parent_id` и материализованный путь `path` типа `ltree` из идентификаторов предков, с GiST-индексом. Поддерево — один запрос по префиксу пути. Полные имена собираются в памяти из списка локаций страны.

**Последствия.** Поддерево и предки читаются одним индексируемым запросом без рекурсии. Путь строится из идентификаторов, а не из имён, поэтому переименование не трогает потомков. Перенос узла в другую ветку потребовал бы переписать пути поддерева; сейчас перенос не поддерживается, удаляется только лист без задач.

**Отвергнуто.** Только `parent_id` с рекурсивными CTE (каждая выборка поддерева рекурсивна); nested sets (дорогие вставки); путь из имён (ломается при переименовании).

## ADR-003. Сессии: короткий access-токен в памяти и refresh в HttpOnly-cookie

**Контекст.** SPA ходит в API с разных устройств, включая телефоны уборщиков. Токен в `localStorage` доступен любому внедрённому скрипту; чистые серверные сессии усложняют горизонтальное масштабирование Functions.

**Решение.** JWT HS256 двух типов. Access-токен живёт 60 минут, приходит в теле ответа и хранится только в памяти вкладки. Refresh-токен живёт 30 дней в cookie `HttpOnly; SameSite=Strict; Path=/api/auth` (`Secure` вне локальной разработки). У пользователя есть `token_version`, входящий в оба токена; каждый запрос сверяет его с БД. Выход, деактивация, смена роли или страны и сброс пароля увеличивают версию.

**Последствия.** Скрипт на странице не может прочитать refresh-токен, а `SameSite=Strict` закрывает CSRF для эндпоинтов обновления. Отзыв всех сессий пользователя мгновенный, но каждый запрос делает одно чтение пользователя из БД. Вкладки одного браузера делят cookie, поэтому вкладка следит за сменой пользователя и переключается на реальную сессию.

**Отвергнуто.** Токен в `localStorage` (XSS = кража сессии); stateless JWT без версии (нельзя отозвать до истечения); серверные сессии (общее хранилище сессий для всех инстансов).

## ADR-004. Приватное хранилище фото и короткоживущие SAS-ссылки

**Контекст.** Фото результата видят только исполнитель, менеджеры страны и администраторы. Публичный контейнер отдал бы фото любому, кто угадал или получил адрес.

**Решение.** Контейнер `task-photos` приватный. API при каждом запросе списка фото подписывает ссылки SAS: только чтение, конкретный файл, срок 2 часа. Ссылки выдаются только тем, кто видит задачу. База ссылок настраивается (`BLOB_PUBLIC_URL`), чтобы локально фото шли через прокси dev-сервера.

**Последствия.** Браузер грузит фото напрямую из хранилища, API не проксирует трафик. Пересланная ссылка работает до истечения срока; отзыва отдельной ссылки нет.

**Отвергнуто.** Публичный контейнер; проксирование каждого фото через API (нагрузка на Functions и холодные старты на просмотре галереи).

## ADR-005. Права доступа — чистые функции домена

**Контекст.** Правила «кто что видит и может» нужны в HTTP API, в SSE-сервере (кому слать событие) и в офлайн-синхронизации. Разнесённые по обработчикам проверки расходятся.

**Решение.** Все правила — в `src/domain/services/task_access.py`: видимость задачи, допустимые переходы статусов (отдельный список для уборщика), блокеры отправки на проверку, право отмечать чек-лист. Обработчики, SSE и синхронизация вызывают одни и те же функции. Интерфейс получает `allowed_statuses` и `review_blockers` готовыми в ответе API.

**Последствия.** Правила тестируются юнит-тестами без БД и одинаково действуют во всех точках входа. Интерфейс не дублирует бизнес-правила, он показывает то, что разрешил сервер.

**Отвергнуто.** Проверки внутри обработчиков; правила на клиенте (UI не является средством авторизации).

## ADR-006. Офлайн-очередь изменений статуса

**Контекст.** Уборщики работают в подвалах и на этажах без связи. Полная офлайн-синхронизация с разрешением конфликтов по всем полям несоразмерна задаче.

**Решение.** Офлайн доступна только смена статуса своих задач. Изменения копятся в очереди на устройстве с меткой времени и отправляются пачкой `POST /sync/batch` (до 200). Сервер применяет каждое изменение в своей вложенной транзакции и отклоняет те, после которых задача менялась на сервере, или недопустимые переходы. Ответ перечисляет, что применено и что отклонено.

**Последствия.** Конфликты разрешаются правилом «сервер новее — офлайн-изменение отклонено» с объяснением пользователю. Комментарии и загрузка фото офлайн недоступны, интерфейс об этом сообщает.

**Отвергнуто.** CRDT или полная репликация (сложность); «последняя запись побеждает» (тихо затирает решения менеджера).

## ADR-007. Тексты на двух языках в каталоге на сервере

**Контекст.** Интерфейс на русском и английском. Сервер формирует сообщения об ошибках, результаты импорта и офлайн-синхронизации и тексты push-уведомлений, которые отправляются вне HTTP-запроса.

**Решение.** Каталог фраз `src/translations/phrases.py`: каждая фраза — пара шаблонов EN/RU с одинаковыми параметрами, плюс склонение числительных для русского. Ошибки хранят фразу с параметрами и рендерятся при формировании ответа на языке из `Accept-Language`, который клиент выставляет по выбранному языку. Push-подписка хранит язык своего устройства. Тест проверяет, что у каждой фразы есть оба языка с одинаковыми параметрами.

**Последствия.** Все серверные тексты в одном месте, фронтенду не нужен справочник кодов ошибок. Добавить язык — дописать колонку в каталоге и словарь интерфейса.

**Отвергнуто.** Коды ошибок с переводом на фронтенде (не покрывает push, импорт и синхронизацию; два источника правды); gettext (тяжеловесно для двух языков и не даёт проверки параметров типами).

## ADR-008. Ограничение попыток входа в базе данных

**Контекст.** Вход по паролю нужно защитить от перебора. Azure Functions масштабируются на несколько инстансов, у каждого своя память.

**Решение.** Неудачные попытки пишутся в таблицу `login_failures` по email в нижнем регистре. Пять неудач за 15 минут блокируют вход для этого email с ответом `429` и `Retry-After`. Успешный вход очищает счётчик. Неизвестные email считаются так же, как существующие.

**Последствия.** Счётчик общий для всех инстансов. Злоумышленник может на 15 минут заблокировать вход чужому аккаунту — это сознательный компромисс; ограничение по IP оставлено шлюзу (Azure Front Door / API Management). Параллельные попытки могут на несколько штук превысить лимит до блокировки.

**Отвергнуто.** Счётчик в памяти инстанса (обходится масштабированием); Redis (новый компонент ради одной таблицы); капча (ухудшает вход с телефона).
